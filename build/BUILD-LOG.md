# Build log

Overnight build of Content Engine from `spec/`, milestone by milestone. Each entry: what was built, how the "done when" was verified, and deviations from spec.

## M0 — Walking skeleton (2026-08-12)

**Built:** Full `build/` scaffold per `spec/structure.md`. One Bun process: Hono API on `127.0.0.1:4321`, `bun:sqlite` DB at `data/content-engine.db` with idempotent numbered migrations (`PRAGMA user_version`) applying the full schema from `schema.sql` and seeding default settings (30-min interval, both starter prompts, voice count 5). `scheduler.ts` with `runOnce()` (per-source isolation, 3-attempt retries with backoff, attempt-trace recording into `run_sources` — retries are M1 scope but were cheap to include at birth), RSS/Atom fetcher on `fast-xml-parser` with dedupe by `(source_id, external_id)` and the "initial import" rule (first fetch of a new source marks everything `skipped`/"initial import"). Source CRUD with per-type validation (RSS validated by fetching once, feed title becomes display name; HN singleton; X handle normalization; YouTube handle→channel_id resolution — resolution lives in `fetchers/youtube.ts` since sources CRUD needs it, full YouTube milestone comes later). React/Vite SPA: five routes, design tokens (three-state light/dark from the styleguide), Nav/Card/Chip/Button/Field components, functional Inbox (filter chips, cards, empty state, Run check now) and Sources pages, functional Runs list (fleshed out in M1), Editor and Settings shells. API-unreachable banner. `bun run dev` = server + Vite with `/api` proxy; `bun run build` + `bun run start` = single-process serving of `web/dist`.

**Verified done-when:** `bun run dev` boots both processes (checked the Vite proxy answers `/api/settings` on :5173 and the server on :4321). Added `https://hnrss.org/frontpage` as an RSS source over the API → POST `/api/runs/trigger` → run #1 recorded 20 new entries; `GET /api/entries` shows them with `state=new` (visible in the Inbox, which lists all non-dismissed entries until the filter exists). Second trigger deduped to 0 new. Killed and restarted the server — entries, source, and runs all intact (SQLite WAL).

**Deviations (M0):** (1) Retry/backoff logic landed in M0's `runOnce()` rather than waiting for M1 — no behavior difference for M0's happy path. (2) Added `source_type`/`source_label` denormalized columns on `entries` and a `channel_id` column on `sources` (plans call for both behaviors; the core schema list just doesn't spell out the columns). (3) Runs totals stored as three columns (`new_count`/`matched_count`/`failed_count`) instead of an opaque "totals" blob. (4) Added `web/src/styles/app.css` next to `tokens.css` for shared component styles — structure.md only names `tokens.css`; keeping raw tokens separate from component CSS seemed truer to its intent. (5) `bun` was not installed on this machine — installed Bun 1.3.14 (plus `unzip`) system-side; nothing in the repo depends on that beyond `bun` being on PATH.

## M3 — Taste filter & Telegram (2026-08-12)

**Built:** `llm/claude.ts` — the only place `claude -p` is spawned; full prompt via stdin (argv is size-limited and visible in `ps`), 60s timeout (120s for generation), kill-on-timeout, one fresh-call retry on unparseable output, and a distinct `ClaudeUnavailableError` for CLI-missing/logged-out. `llm/filter.ts` — taste prompt from settings wrapped in a code-owned MATCH/SKIP one-line contract. Filter pass inside `runOnce()` after fetching: serial over every pending entry including leftovers from previous runs; per-entry parse failure leaves the entry pending; `ClaudeUnavailableError` or 3 consecutive errors aborts the pass and records a run-level error (new `runs.error_text` column via additive migration 2 — exercising the migration path). Notify pass: Telegram message per matched entry (plain text: title / source / filter's take / URL), strictly on the `new→notified` transition so a refilter can never re-notify; send failure recorded on the run and the entry stays `new` for a resend next run. Inbox now shows matched-only entries (per mockup), with the "All caught up" empty state showing "N sources checked, M entries filtered" from the last run. Runs page renders run-level errors with the claude/Telegram hints.

**Verified done-when:** Live run filtered real pending HN/RSS entries — verdicts stored with one-line reasons (e.g. "The Ultimate Horse" → SKIP "no connection to AI economics…"). Seeded a taste-matching entry: MATCH with a specific reason, `matched_count` attributed to the run. Filter-failure path: restarted the server with `claude` off PATH → run #12 recorded exactly "claude -p failed — is the CLI installed and logged in?" and entries stayed `pending`; after restoring PATH, run #13 re-filtered the same entry to `matched` — nothing lost. Telegram-failure path: with no token configured the run records "Telegram send failed … not configured — add the bot token and chat ID in Settings" and the entry stays `state=new`.

**Needs real credentials to test:** actual Telegram delivery of a match (message content/format) and the `new→notified` transition on success. Everything up to the send — including the resend-next-run behavior — is exercised.

## M4 — Thread studio (2026-08-12)

**Built:** `llm/generator.ts` — composes the `claude -p` input as: generation prompt (settings) → voice examples (last N posted finals, newest first; section omitted entirely when the pool is empty) → item material (title/URL/content, plus transcript for YouTube with beginning+middle-sample truncation at ~15k words) → JSON-array output contract in code. `composeGenerationPrompt()` is exported separately so the exact prompt is inspectable. `routes/threads.ts`: POST `/api/entries/:id/draft` (retries the transcript fetch for YouTube entries missing one, generates, then replaces-or-creates the thread row only AFTER a successful parse — a failed regenerate never loses the previous draft), debounced PUT for edits, `posted` (current edited text → `final_text`, entry → `posted`), and `unposted` (the spec's cheap-undo open question — included since trivial). Editor page per its mockup: breadcrumb, serif title, left column with filter's take + source material (transcript in a scrollable mono block with word count when present), right column of auto-sizing tweet blocks (`field-sizing: content`, 120px min-height), n/total labels, live char counts flipping crimson-bold over 280 (visual only), + Add tweet, Regenerate behind a confirm, Copy all (blank-line separated, no numbering), green Mark as posted with its caption, voice note, inline generation-error card with Retry. Inbox "Draft thread" navigates with `?draft=1` so generation starts on arrival.

**Verified done-when:** Matched entry #491 generated a 4-tweet draft (real `claude -p` call, ~30s). Edited the draft over the API with a marker string — persisted through GET. Marked as posted → `final_text` + `posted_at` stored, entry `state=posted`. Then composed the next generation's prompt for a different item: it contains the edited final text verbatim under "## Voice examples" with voiceCount=1 — the feedback loop demonstrably closes. Copy-all is client-side clipboard (`join("\n\n")`), exercised in the browser pass at the end.
