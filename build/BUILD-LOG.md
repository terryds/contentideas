# Build log

Overnight build of Content Engine from `spec/`, milestone by milestone. Each entry: what was built, how the "done when" was verified, and deviations from spec.

## M0 — Walking skeleton (2026-08-12)

**Built:** Full `build/` scaffold per `spec/structure.md`. One Bun process: Hono API on `127.0.0.1:4321`, `bun:sqlite` DB at `data/content-engine.db` with idempotent numbered migrations (`PRAGMA user_version`) applying the full schema from `schema.sql` and seeding default settings (30-min interval, both starter prompts, voice count 5). `scheduler.ts` with `runOnce()` (per-source isolation, 3-attempt retries with backoff, attempt-trace recording into `run_sources` — retries are M1 scope but were cheap to include at birth), RSS/Atom fetcher on `fast-xml-parser` with dedupe by `(source_id, external_id)` and the "initial import" rule (first fetch of a new source marks everything `skipped`/"initial import"). Source CRUD with per-type validation (RSS validated by fetching once, feed title becomes display name; HN singleton; X handle normalization; YouTube handle→channel_id resolution — resolution lives in `fetchers/youtube.ts` since sources CRUD needs it, full YouTube milestone comes later). React/Vite SPA: five routes, design tokens (three-state light/dark from the styleguide), Nav/Card/Chip/Button/Field components, functional Inbox (filter chips, cards, empty state, Run check now) and Sources pages, functional Runs list (fleshed out in M1), Editor and Settings shells. API-unreachable banner. `bun run dev` = server + Vite with `/api` proxy; `bun run build` + `bun run start` = single-process serving of `web/dist`.

**Verified done-when:** `bun run dev` boots both processes (checked the Vite proxy answers `/api/settings` on :5173 and the server on :4321). Added `https://hnrss.org/frontpage` as an RSS source over the API → POST `/api/runs/trigger` → run #1 recorded 20 new entries; `GET /api/entries` shows them with `state=new` (visible in the Inbox, which lists all non-dismissed entries until the filter exists). Second trigger deduped to 0 new. Killed and restarted the server — entries, source, and runs all intact (SQLite WAL).

**Deviations (M0):** (1) Retry/backoff logic landed in M0's `runOnce()` rather than waiting for M1 — no behavior difference for M0's happy path. (2) Added `source_type`/`source_label` denormalized columns on `entries` and a `channel_id` column on `sources` (plans call for both behaviors; the core schema list just doesn't spell out the columns). (3) Runs totals stored as three columns (`new_count`/`matched_count`/`failed_count`) instead of an opaque "totals" blob. (4) Added `web/src/styles/app.css` next to `tokens.css` for shared component styles — structure.md only names `tokens.css`; keeping raw tokens separate from component CSS seemed truer to its intent. (5) `bun` was not installed on this machine — installed Bun 1.3.14 (plus `unzip`) system-side; nothing in the repo depends on that beyond `bun` being on PATH.

## M1 — Scheduler, run history, HN (2026-08-12)

**Built:** `Bun.cron` registration from the interval setting (`registerSchedule()` — stops the old handle and registers a new one when the setting changes; wired into boot and the settings PUT). Interval→cron mapping includes a hidden `1m` test value not offered in the UI. `nextRunAt()` via `Bun.cron.parse()` surfaces "next check at HH:MM" in the Inbox header and the Runs empty state. HN front-page fetcher (Firebase API, top-30 slice, item fetches in parallel, one missing item never fails the page; content = points + comment count + article URL; entry URL = the HN discussion page to match the mockup's "Open on HN"). Runs page: newest-first cards with expandable per-source table, attempt counts, error trace block, and plain-language hints (407→Floxy settings link, "not configured"→Settings, claude→CLI hint) with 4s polling while open. 30-day pruning runs at boot (from M0). Retries/backoff/attempt traces were already in from M0.

**Verified done-when:** Set `check_interval=1m` (test value) directly in SQLite, restarted, added the HN source plus a deliberately dead feed URL (`hnrss.org/this-feed-does-not-exist-404`, inserted via SQL since add-time validation correctly refuses it). Runs #3 (13:53) and #4 (13:54) fired unattended with `trigger=cron`. Run #3 shows the broken source `failed` after 3 attempts with the human-readable trace ("attempt 1 13:53:00 → Feed fetch failed: HTTP 404 Not Found … giving up after 3 attempts") while `hn:frontpage` (30 new, initial import) and the live feed succeeded in the same run — per-source isolation confirmed.

**Deviations:** `Bun.cron` in Bun 1.3.14 is minute-granularity (5-field) and its in-process form takes `(expression, handler)` — no title. Run-status semantics pinned as: source `ok` (first try) / `retrying` (succeeded after retries, surfaces as amber) / `failed`; run chip shows crimson "n failed" > amber "Retries" > green OK. The mockup was ambiguous here (showed OK with attempts=2).
